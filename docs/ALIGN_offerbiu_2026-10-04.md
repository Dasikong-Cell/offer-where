## 二、🔴 检测中最值钱的发现：三个**静默失效**的控件

这些不是「比 offerbiu 少个功能」，而是**本地的现有功能在真实数据上不生效，且页面看起来完全正常**。

| 控件 | 真实库覆盖率 | 实际后果 |
|---|---|---|
| 校招信息库「全部类型」下拉 | `job_type` = **0 / 2506（0.0%）** | 选任何具体类型（产品岗/技术岗/…）都得到「没有匹配的岗位」；下拉里那 10 个选项**一个都筛不出来** |
| 校招信息库「全部截止状态」下拉 | `deadline` = **0 / 2506（0.0%）** | 4 档里「7 天内截止」「已截止」**恒 0 条**；「未截止」因 `days === null` 判真而**等于全量**（把「没填」当成了「未截止」） |
| 总览「3 天内截止」/ 我的投递「待投递 · 3 天内截止」 | 同上 | **永远显示 0 个**（上一轮新加的筛选按钮也在其中） |

根因（已读码确认，不是猜的）：`function deadlineInfo(dl)` **只读 `dl` 本身，没有兜底**，
`raw` 为空就返回 `{ days: null }`；筛选逻辑里 `dl==='open'` 分支把 `days === null` 判为通过。
采集端则从来没写入过 `deadline` 与 `job_type`（`offerbiuCollect.js` 里 `TAGS_RE` 只用来
**裁掉职位名尾部的标签文字**，并不落库）。

⇒ **建议优先级高于任何「抄 offerbiu」的功能**：要么把这两列填上（数据管道），
要么把这两个下拉收起来并在界面上说明，别留「选了没反应也不解释」的控件。

## 六、本地**多于** offerbiu 的能力

- **总览**：开箱自检 / 投递漏斗（四向覆盖口径，明示不虚报覆盖率）/ AI 能力 / 运行健康 / 平台通道
- **简历管理**：候选人档案 / JD 长图查看器 / 求职信模板
- **自动填充**：内置 CDP 表单通道 + 表单记忆（**不用装浏览器插件**）

## 七、结论

1. **页级别完全对齐**，无整页遗漏；差异集中在页内功能点。
2. **最该先修的不是缺口，而是三个静默失效的控件**（类型 / 截止状态 / 3 天内截止）——
   它们让「校招信息库」和总览的截止提示**看起来在工作**，实际恒空，且不报错。
3. **校招信息库的多数缺口其实数据就绪**（届别、免笔试、央国企、研究所、外企都在 `card_text` 里），
   属于**高性价比**：解析一列 + 加几个筛选即可，不必重写采集。
4. **一处结构性差异需先定方向**：自动填充的「多条目结构化信息」不是加字段能解决的，
   要先决定「本地是否也走『简历信息库 + 多条目』这条路」。
5. 其余为**收尾级别**（补筛选 / 把已有数据在个人中心汇总），不动数据模型。

## 三个可复用的教训（已写进 skill / 记忆）

1. **断言必须先造出「能区分」的数据。** 第一版 E2E 断言是「未截止 < 全量」和
   「未填截止那档全是『招满为止』」：隔离副本库里只有两条岗位、且**都带截止日**
   ⇒ 前者必红，后者在 0 条上 `every()` **恒真**（一个恒绿的假断言）。
   ⇒ 补造一条「无截止日」的岗位，断言才变成「恰好 2 条且不含它 / 恰好 1 条且就是它」。
2. **破坏性对照被外部杀掉时 `finally` 不执行。** 脚本超时（SIGTERM）把产物
   **停在了被污染状态**，而门禁看起来照跑不误（当时合约报「基线本身就红」才发现）。
   ⇒ 加 sidecar 备份 + 启动即校验还原 + SIGTERM 处理器；且 sidecar **不能放在 `public/`**
   （会被打进产物、也会出现在 `git status` 里），要放 `_tools/`（已 gitignore）。
3. **跨 realm 的 `instanceof` 是静默失效源。** `vm` 沙箱里的 `Date` 与宿主的 `Date`
   不是同一个构造函数 ⇒ `now instanceof Date` 恒假、注入的「现在」被无视，
   测试「看着在跑、其实在用真实时钟」。⇒ 改成按能力判（`typeof now.getFullYear === 'function'`）。

## 改了什么

### 1. 新增结构化解析器 `server/services/parseCardMeta.ts`（303 行，纯函数、零 IO）

`card_text` 是 offerbiu 卡片被压平的一行文本（`公司 更新 9月11日 岗位 行业 性质 地点 届别 时间 要求`），
信息密度高但**全是文本** ⇒「按届别筛」只能退化成全文 `includes`，就是 A 批那三个静默失效控件的**同一病根**。
入库路径（`upsertJob`）与存量回填（`scripts/backfill_card_meta.ts`）**共用同一份模块**，绝不各写一份。

| 列 | 判据 | 实测精度 |
|---|---|---|
| `grad_year` | 正则 `(?<!\d)(20\d\d)\s*届`（**只认 4 位完整写法**） | **963 / 963 命中、0 假阳性**（`27届秋招-产品助理` 这类职位名短写**不认**） |
| `tags` | **空白切词后的 token 等值**，不做子串搜索 | 12 类共 3961 次打标、**0 假阳性** |
| `deadline` | 🔴 **结构性锚点**：届别 token 之后**恰好一个空白** | **113 / 113**（距离实测 **min = max = 1**） |

三个关键决策（都是「宁少不错」）：

- 🔴 **token 等值，绝不子串。** 子串会把**行业大类** `政府/事业单位/社会组织` 误判成企业性质
  「事业单位」（实测 7 条）⇒ 行业名被当成企业性质。`A/B` 形式（`外企/合资`，实测 3 条）
  **要求每一段都是已知性质**才认，整体拒绝则一条都不打。
- 🔴 **「研究所」不是企业性质，是公司名关键词。** token 等值匹配实测 **0 条**、
  公司名含「研究所」实测 **40 条**。⇒ 按真实语义实现（**只在首段公司名里找**，避免职位名里的
  同名词误报）+ 在 `hint` 里写明 —— **语义与字面不一致的标签没有 hint 就是在骗用户**。
- 🔴 **`deadline` 不靠启发式窗口。** 「届别之后恰好 1 个空白」让顶部 `更新 9月11日`（**没有年份**）
  与正文里的日期都**天然不命中**；`尽快投递`/`招满为止` 后面没有日期 ⇒ `null`
  （而不是被当成一个「很像日期」的值）。语义已交叉确认：巡检表格表头 `… | 届别 | 时间 | 要求`，
  同列上 `尽快投递` 与 `2026/10/28` 交替出现，且 offerbiu 有「近7天截止」筛选。

### 2. 列扩展走已有通道

`grad_year TEXT` / `tags TEXT`（JSON 数组）/ `deadline TEXT`；`tags` 落库前过**服务端白名单**
`CARD_TAG_KEYS` ⇒ 脏值进不了库，前端也就**不可能**渲染出一个「点下去筛不出东西」的 chip。

⚠️ 白名单是**显式清单**、不是 `CARD_TAG_DEFS` 的反向推导（破坏性对照 K13 专门验证：从白名单里
删掉 `tags` 必须被打红）——「只落库不上控制台」的标签（`民企` 539 条 / `合资` / `暑期实习`）
与「可落库值」是**两个集合**。

### 3. 控制台 `public/console.html` —— P1-a 四项（`ui:true` 的 8 个 chip）

| # | 落点 | 改法 |
|---|---|---|
| B1 | 届别筛选 | 下拉**候选只取数据实测值**（值 + 条数）⇒ 新平台/新城市**自动出现** |
| B2 | 快捷标签 | chip 行；🔴 **定义由 `GET /api/jobs` 的 `tagDefs` 下发**（服务端 `CARD_UI_TAGS` 是唯一真相源，前端只 `JSON.parse`、**不抄第二份规则**） |
| B3 | 重置筛选 | 清条件 + 重取数据；🔴 **不动视图**（视图是「我怎么看」不是「我筛什么」） |
| B4 | 卡片视图 | 表格 ⇄ 卡片**互斥渲染**；🔴 **只重建可见那块**（不可见那块用 sentinel 证明**没被重建**） |

两处计数口径最容易错、已钉成断言：

- 🔴 **chip 上的数字必须 = 点下去会得到的条数。** 多选状态下要用 **`已选 ∪ {自己}`** 去算：
  按「只有自己」算出来的数会**比实际结果小**（`秋招` 实测 3 vs 2）—— 数字与结果对不上，
  用户会以为筛选坏了。
- 🔴 **`dataset.filled` 必须从校招信息库删净。** A 批用它做「快筛条只建一次」的优化，但校招
  信息库的候选集是**活的**（新平台/新城市/新届别）⇒ 沿用会让**新值永远进不了下拉且不报错**。
  只有「重置筛选」这种纯前端状态才允许保留一次性初始化。

## 三个可复用的教训（已写进 skill / 记忆）

1. **插一列 ⇒ 全仓搜 `nth-child`。** 给 jobs 表第 4 列插「届别」后，「截止」从第 6 列变成第 7 列；
   E2E 里写死的 `td:nth-child(6)` **不报错、只是读到隔壁列**（打印出「实际「手动录入」」这种
   驴唇不对马嘴的值）。**列序变了就等于所有列下标断言同时失效**，且失败信息会指向错误的方向。
2. **新增一个受管维度 ⇒ 所有 stub 数据要补那一维。** `jobsFilterAvailability()` 多了「届别」之后，
   A 批定点探针的 stub 只有 `job_type`/`deadline` ⇒ 既有断言「数据补上后自动解禁」**变红**，
   而断言文案只说类型/截止，**指不到真凶**（下次直接看受管清单有几个维度）。
3. **新造的测试数据不许改变既有断言的判据人口。** B 批三条岗位若不带截止日 ⇒ 落进
   「未填截止」档 ⇒ 打红「恰好 1 条」的既有断言。**造数据时先想「它会不会挤进别人的样本」**。

外加一条仪器级的（写进 `contract-assertion-discipline`）：

🔴 **「没红」要再分两种：全过 vs 脚本自己崩了。** 第一版对照脚本的 K13 把变异点选成「删掉
INSERT 的一个参数」⇒ `better-sqlite3` 真实抛 `SqliteError: 21 values for 22 columns` ⇒
**合约脚本在第 3 段就崩了、汇总行根本没打印** ⇒ 收集到的 `reds` 为空，看起来像「断言失守」。
⇒ 判据必须是**输出里有没有汇总行**（全绿时脚本**不会**打印「失败项」），且**变异点别选在会改
可运行性的地方**。
