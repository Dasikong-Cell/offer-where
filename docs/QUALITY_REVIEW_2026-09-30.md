## 三、发现的缺陷与整改

### 🔴 P0 —— `PATCH /api/jobs/:id` 列名 SQL 注入

**现象（实测，隔离库）**

```
PATCH /api/jobs/<id1>
body = { "company = 'INJECTED-ALL-ROWS', position = ?, city = ?, salary = ? --": "P" }

→ HTTP 200 {"success":true}
→ 库里 3 条**互不相同**的岗位，company 全部变成 INJECTED-ALL-ROWS
```

**根因（三处叠加）**

1. `server/index.ts` 的路由把 `req.body` **整包**转发：`db.updateJob(req.params.id, req.body || {})`
2. `server/db.ts` 的 `updateJob` 用 **对象键**拼列名：`for (const key of Object.keys(updates)) fields.push(\`${key} = ?\`)\`
3. 拼出的 SQL 是 `UPDATE jobs SET ... WHERE id = ?`，载荷里的 `--` 把 `WHERE id = ?` **整段注释掉** ⇒ 影响全部行

> ⚠️ TypeScript 的 `Partial<Pick<JobRow, ...>>` **只是编译期约束**。`req.body` 是 `any`，运行时没有任何键名校验 —— 这是「类型看着安全、运行时没有防线」的典型。

**影响**：能访问到服务的人可用一条请求改写全表（`jobs` 是匹配分、求职信、定制简历的共同上游），也能把任意表达式写进可读列再读出来 → 数据泄露。反过来，**本机自用场景影响有限，但 `start_lan.bat` 一开（同网段任何人拿得到页面注入的令牌）就成立**。

**修法（两道独立防线）**

- `db.ts`：新增 `collectUpdateFields()`，**按列名白名单遍历**，键名只可能来自常量。注入面被结构性消除（不是过滤黑名单）。
- `index.ts`：路由改用同一份清单（`db.JOB_UPDATABLE`，真相源在 `db.ts`）显式挑字段，未知键直接丢弃 —— 保留旧客户端「多传字段也不报错」的兼容性。
- 顺带修掉一个误导：原先「没有可更新字段」也 `return false`，与「岗位不存在」共用 404，空 body 会被报成「岗位不存在」。现在区分 400 / 404。

**验证**

|                            | 修复前                     | 修复后                                    |
| -------------------------- | ----------------------- | -------------------------------------- |
| `_tools/_inject_probe.mjs` | 载荷被接受、**全表改写**（原判据 4/4） | **7/7**：载荷被拒（400「没有可更新的字段」）、**0 行被改写** |
| 正向对照                       | —                       | 白名单字段（city/status）**仍可正常更新** ✅         |
| 合约护栏（+5 条）                 | 全部红                     | 全部绿                                    |

> 正向对照是必须的：否则「注入不生效」可以靠「接口整个坏掉」来满足。

### 🟠 P1 —— DB 备份保留策略名不副实（承诺留 3 份，实际只留 1 份）

**现象（实测，隔离库）**

```
场景：3 份主备份，各带 -wal / -shm 伴生文件（共 9 项），keepDbBackups = 3
修复前 → 报告 deleted=6，结果只剩 chat.db.bak-3000{,-shm,-wal}  ← 只留了 1 份
```

**现场旁证**：真实 `data/` 里当时只剩  
`chat.db.bak-1789794465303-shm` / `chat.db.bak-1789794879660-shm` / `chat.db.bak-1789794879660-wal`  
—— **一份 `.db` 主备份都没有**，只剩伴生文件。

**根因**：`dataCleanup.ts` 按**文件名前缀** `chat.db.bak-` 无差别收集，而 SQLite 的 WAL 伴生文件  
`chat.db.bak-<ts>-wal` / `-shm` **同样命中该前缀** ⇒ 它们被当成「一份备份」参与 mtime 排序、**挤占保留名额**。  
若伴生文件的 mtime 晚于主文件，名额被占满 ⇒ **真正可用的备份一份不剩** —— 灾难恢复能力归零。

**修法**：以「去掉 `-wal`/`-shm` 后缀的基名」为分组键，按组内最新 mtime 排序，**整组保留 / 整组删除** —— 伴生文件跟着它的主备份一起留或一起走。

**验证**

|                                      | 修复前             | 修复后                                                          |
| ------------------------------------ | --------------- | ------------------------------------------------------------ |
| `_tools/_backup_retention_probe.mts` | 2 / 4（场景 1 两条红） | **8 / 8**（含新增场景 3：4 组主+伴生保留 3 组 → 最旧那组**整组**消失、删除计数 = 3、无孤儿） |
| 合约护栏（+2 条）                           | 全红              | 全绿                                                           |

### 🟡 P2 —— 简历备份无限累积（且含个人信息）

**根因**：`/api/resume/upload` 每次重传都把旧简历改名成 `resume_*.pdf.bak.<ts>`（`server/index.ts`），  
**此前没有任何地方回收** ⇒ 每重传一次就在 `data/` 里多留一份含姓名/电话/邮箱的简历副本。

**修法**：纳入 `cleanupData`，保留最近 2 份（`--keep-resume` 可调），并计入清理报告。  
**验证**：合约护栏 +1 条（断言 `keepResumeBackups` 在「选项声明 / 默认值 / 保留计算」三处齐全）；`_backup_retention_probe.mts` 场景 3 的 `deleted` 计数同时覆盖简历备份。

---

### 🟡 P2 —— 清理报告会谎报「已释放」的空间

**现象（实测撞见）**：某次跑清理，报告写 `DB备份 删除 1`，而目录里 4 个备份**一个都没少**。

**根因**：三处删除点都是「**先** `deleted++` / `freedBytes += size`，**再** `unlink`」，而 `unlink` 抛的错被  
`catch { }` 吞掉 ⇒ 只要删除失败（文件被占用、权限不足、环境拒绝），报告仍会宣称释放了并未释放的空间。

**修法**：改成「**先删后计**」—— 只有 `unlink` 真的成功才计数；`dryRun` 走单独的「只统计」分支。

**验证**：`_backup_retention_probe.mts` 场景 4 把 `unlink` 打桩成**恒失败**（确定性，不依赖环境），  
要求 `deleted === 0`、`freedBytes === 0`，且文件确实都还在。

> 这条是「先取证再结论」的副产品：原本只是探针被环境的删除护栏拦住，结果暴露出报告本身在说谎。

---

### 🟡 P2 —— 空 body PATCH 误报「岗位不存在」

**根因**：`updateJob` 在「没有可更新字段」时 `return false`，路由把 `false` 统一解释成 404。  
**修法**：路由区分两种情况 —— 岗位不存在 → 404；岗位存在但无字段 → 400「没有可更新的字段」。  
（已在 P0 的同一处改动里一并处理。）

## 五、本轮未覆盖 / 已知边界（诚实说明）

1. **公网暴露、多租户、账号体系**：架构级缺失，不在本轮口径内。当前设计是「本机或可信局域网」。
2. **`HOST=0.0.0.0` 下的同网段信任模型**：同网段任何设备打开控制台都会**拿到页面注入的令牌**，因此能调用有副作用的接口。这是既有设计（令牌只挡跨站/非浏览器调用，不区分同网段陌生人）。⇒ **仅限可信 Wi-Fi，勿做端口映射。**
3. **`data/` 无自动体积上限**：默认 3000MB 仅**告警**，不自动删。当前 810.5 MB（`browser` 登录态 506MB + `jd_images` 234MB 是有意不清理的）。
4. **`data/smoke/`（1.3MB）等历史调试产物**：不在清理范围内。这是开发期遗留，非应用产生的常态数据。
5. **没跑真实投递链路**（见 2.3）。
6. **`data/browser` 与 `data/jd_images` 不清理是有意为之**（登录态 / JD 证据），但它们是 `data/` 体积的 91%。
