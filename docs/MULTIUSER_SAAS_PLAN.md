# 多用户公网版 —— 技术方案与可行性评估

> 目标：评估「把 OfferWhere 做成公网多用户产品，让其他人也能使用」的可行性。
> 结论日期：2026-09-30 ｜ 依据：本机代码实测（107 路由 / 10 表 / 12 平台适配器）+ 既有取证 `BOSS_OPENAPI_PLAN.md`、`COMPETITOR_FORENSICS.md`
> 状态：**待评估，未动工**

---

## 一、结论先行（TL;DR）

| 问题 | 结论 |
|---|---|
| 现有代码能直接部署到服务器给多人用吗？ | **不能**。它操作的是「本机 Chrome 里已登录的招聘账号」，服务器上没有你的浏览器，也没有你的登录态。 |
| 那要做什么？ | 不是「部署」，而是**重写为多用户 SaaS**：用户体系 + 数据隔离 + 云端浏览器集群。 |
| 最大障碍是什么？ | **投递能力**。它依赖真实浏览器会话；上云 = 要维护云端 Chrome 集群 + 住宅代理 + 会话池（架构 C）。 |
| 纯技术工作量？ | **约 3–5 人月**（不含行政流程），且**运维是持续成本**而非一次性。 |
| 行政周期？ | 域名 ICP 备案 **1–2 周**；小程序类目审核视资质 **2–4 周**。 |
| 建议？ | **不建议现在做**。理由见 §六。若坚持要做，§五 给了分阶段路径，但先读 §四 的合规风险。 |

## 二、现状盘点（实测数据）

### 2.1 代码规模

| 项 | 数值 |
|---|---|
| 后端 TS 文件（server + shared） | **72 个** / 19,788 行 |
| 前端文件（React） | 25 个 |
| API 路由 | **107 个** |
| 数据库表 | **10 张** |
| 招聘平台适配器 | **12 个**（boss / 猎聘 / 智联 / 51job / 牛客 / 应届生 / 国聘 / 中国人才热线 / offerbiu / yupao / …） |

### 2.2 🔴 关键事实：10 张表**全部没有用户维度**

```
jobs          -> id, source, company, position, ... (无 user_id)
applications  -> id, platform, company, position, ... (无 user_id)
profile       -> id, data, updated_at              (单行，就是「我」)
sessions      -> id, title, model, ...             (无 user_id)
messages      -> id, session_id, role, content     (经 session 关联)
```

`profile` 表是**单行**的——整个数据库天然假设「只有一个用户，就是我」。
这意味着多用户化不是「加个登录页」，而是**数据模型的地基重做**。

### 2.3 🔴 CDP 依赖：集中在 4 个文件，但它是核心能力

```
server/services/browser.ts
server/services/browserHealth.ts
server/services/cdpDriver.ts        ← 薄封装（execCdpAction / closeAllCdp / listCdpSessions）
server/services/browserHealth.d.ts
```

好消息是**封装很薄**（只有 4 个文件、共 7 处引用）；坏消息是**12 个平台适配器全都建立在它之上**——
投递、自动回复、聊天、简历图这些「真正有价值」的功能，全都要经它操作真浏览器。

### 2.4 投递为什么不能改成纯 HTTP

既有取证（`BOSS_OPENAPI_PLAN.md` §5.4）已论证：

- BOSS 投递带服务端下发的加密签名（`__zp_stoken__` / tk），猎聘带 `X-XSRF-TOKEN` 配套签名
- 纯 HTTP 复现 = 持续对抗平台的签名算法升级 ⇒ **维护成本极高、封号风险大**
- CDP 整页链路是「真浏览器点真按钮」，签名由页面自己算 ⇒ **反而更稳**

⇒ 所以「投递」这个能力**必须**有真实浏览器，这不是实现选择，是物理约束。

## 三、三条架构路线（既有文档已论证，此处复述结论）

| | A. 官方开放平台 | B. 本地会话 + 逆向 JSON | C. 云端会话中继 |
|---|---|---|---|
| 求职者侧可行性 | ❌ 不可行 | ✅ 可行 | ✅ 可行 |
| 本机依赖 | 需固定 IP | 需本机常驻 Chrome | **无** |
| 验证码 | 不涉及 | 仍有 | 用户端基本无感 |
| 维护成本 | 低 | 中 | **高** |
| 合规风险 | 低 | 中 | **中高** |

**A 为什么不可行**（三重阻断，官方文档已核实）：
1. **身份错位**——开放平台的调用主体是「招聘方/服务商」，求职者无法通过实名审核拿到凭证
2. **IP 白名单**——必须从报备过的固定 IP 调用
3. **能力缺失**——**根本不存在**「以求职者身份投递」这个 API，怎么申请都没有

**C 才是产品化的唯一形态**，但它的代价是：**你要维护一个云端浏览器集群**——
远端 Chrome + 会话持久化 + 住宅代理 + 验证码兜底 + Session 池。
这也是同类产品（`COMPETITOR_FORENSICS.md` 取证）验证码「无感」的真正原因：
**那不是用户本机的会话**。

## 四、⚠️ 必须正视的合规风险（请勿跳过）

这一节不是免责声明，是会直接影响你个人安全的部分。

### 4.1 违反平台用户协议

用自动化手段代替人工投递，**违反 BOSS / 猎聘等平台的用户协议**。个人自用是「平台懒得管」；
**一旦做成多用户产品、规模化调用，性质就变了** —— 从「个人小工具」变成「对抗平台风控的服务」。

### 4.2 封号风险的承担者是谁？

**是你，不是你的用户。** 因为：
- 云端会话用的是**你注册的账号**（或你批量注册/租用的账号）
- 平台风控识别到异常，封的是**这些账号**
- 如果你让每个用户绑自己的账号，那你只是「提供了工具」，风险相对可控 —— 但这又回到了「本地工具」的形态

这是一个**结构性矛盾**，不是技术能解决的：
> 云端代操作 ⇒ 需要集中持有账号 ⇒ 账号被封的责任在服务提供方。

### 4.3 个人信息保护（PIPL）

一旦你开始**收集他人的简历**（真实姓名、电话、学历、工作经历），你就是**个人信息处理者**，法律义务包括：
- 明示告知 + 单独同意（简历属敏感个人信息）
- 加密存储、最小必要、可删除
- 若泄露，**你要承担法律责任**（PIPL 罚则可到上一年营业额 5% 或 5000 万元）

**这是我认为最需要你认真权衡的一条**：你现在处理的是自己的简历，没问题；
开始处理别人的，责任性质就完全不同了。

## 五、如果坚持要做：分阶段路径

> 前提：你已读完 §四 并接受相应风险。

### 阶段 0：可行性验证（1–2 周，无行政依赖）
**目标：先验证「云端能不能跑通投递」，再谈其他。**

- [ ] 在一台云主机上跑通「远端 Chrome + CDP 连接 + 登录 BOSS + 投递 1 个职位」
- [ ] 验证住宅代理是否必需（机房 IP 极可能被风控直接拦）
- [ ] 实测：单账号连续投递多少会被封

**这一步的产出决定后面还做不做。** 如果云主机 IP 一登录就被风控，整个方案立刻终止，节省后面全部投入。

### 阶段 1：多用户化改造（4–6 周）
- [ ] 数据模型：10 张表加 `user_id`，`profile` 从单行改多行；写迁移脚本
- [ ] 用户体系：注册/登录（微信登录 or 手机号）、会话管理
- [ ] 数据隔离：**所有 107 个路由**加用户过滤；这一条最容易漏，必须有自动化测试兜底
- [ ] 存储隔离：简历文件按用户分目录 + 加密
- [ ] 把现有「令牌鉴权」升级为真正的用户鉴权

### 阶段 2：云端投递能力（6–10 周）
- [ ] 云端 Chrome 集群（容器化 + 资源隔离）
- [ ] 会话池 + 持久化 + 健康检查
- [ ] 住宅代理接入（成本：按流量计费，不便宜）
- [ ] 验证码兜底（打码服务 or 人工）
- [ ] 限流与队列（防止单用户拖垮集群）

### 阶段 3：合规与发布（行政 3–6 周，与阶段 2 可并行）
- [ ] 域名注册 + **ICP 备案**
- [ ] HTTPS 证书
- [ ] 隐私政策 + 用户协议 + 个人信息收集告知
- [ ] 微信后台配置 request 合法域名
- [ ] 小程序类目审核（可能需要资质证明）
- [ ] 等保测评（若涉及大量个人信息，可能被要求）

## 六、我的建议：不建议现在做

### 6.1 成本收益不成立

| 项 | 投入 |
|---|---|
| 开发 | 3–5 人月 |
| 运维 | **持续**：云主机 + 代理流量 + 打码服务，每月数百到数千元 |
| 行政 | 备案 + 审核 1–2 月 |
| 风险 | 账号被封 + PIPL 责任 |

而收益是「别人能用」——但**别人真正需要的是「一个能替自己投简历的工具」，而不是「登录你的网站」**。

### 6.2 更关键：这个产品的正确分发形态是「本地工具」

你的 GitHub Release 已经发布了 `OfferWhere-Setup.exe`（379 MB）。任何人下载双击，
就能在自己电脑上装一套**完整**系统——投递、自动回复全都有，用的是**他自己的** Chrome 登录态。

对比一下：

| | 本地安装包（现状） | 云端多用户版 |
|---|---|---|
| 用户数据在哪 | **用户自己电脑** | 你的服务器（你要担责） |
| 账号风险谁承担 | **用户自己** | **你** |
| 投递能力 | ✅ 完整 | ⚠️ 要重建云端浏览器集群 |
| 你的成本 | 0 | 开发数月 + 持续运维费 |
| 你的法律风险 | **无** | PIPL + 平台协议 |

**「本地安装包」在每一项上都更好**，而且你已经做好了。

### 6.3 真正值得做的改进（成本低、见效快）

如果你的目标是「让别人也能用上」，我建议把力气花在这里：

1. **降低安装门槛**——现在 379 MB 的 exe，首次使用要自己启动 Chrome 调试端口（`LOGIN_GUIDE.md`）
2. **做好首次使用引导**——装完告诉他：去哪登录 BOSS、怎么确认登录成功
3. **写一份「给使用者」的说明**——不是给开发者看的 README，是给普通用户看的
4. **可选的：做一个演示视频/图文**，让人 3 分钟看懂这是什么

这些做完，别人拿到安装包就能顺利跑起来——**这才是真正解决「别人用不上」的问题**。
